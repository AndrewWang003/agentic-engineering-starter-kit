# Unknowns-First Task Reference

## 1. Reference 名称

**Unknowns-First Task Reference**

中文名称：

**未知量优先的任务协作参考**

---

## 2. Reference 目的

在复杂任务开始前，优先识别和减少关键未知量，避免 AI Agent 在错误方向上高速执行。

本参考不追求写出一段“完美提示词”，而是提供一套人机协作流程：

1. 执行前发现盲点；
2. 找出需要人类决策的问题；
3. 用原型暴露隐性偏好；
4. 先审核计划，再允许实施；
5. 执行中记录偏差；
6. 根据风险决定继续还是暂停；
7. 实施后验证结果；
8. 确认人类真正理解改动。

核心原则：

> Agent 越强，越不能直接把模糊任务交给它执行。

---

# 3. 核心概念

## 3.1 地图与领土

### 地图 Map

人类提供给 Agent 的信息，包括：

- 提示词；
- 项目文档；
- 任务合同；
- 架构说明；
- 需求描述；
- 示例；
- 约束；
- 验收标准。

### 领土 Territory

任务实际发生的真实环境，包括：

- 代码库；
- 数据；
- 历史兼容逻辑；
- 外部依赖；
- 运行环境；
- 用户行为；
- 业务规则；
- 隐藏的技术限制。

### 地图与领土之间的差距

Agent 出错通常不只是因为模型能力不足，也可能因为：

- 地图不完整；
- 地图已经过时；
- 地图与真实代码不一致；
- 人类遗漏关键约束；
- 人类自己也不了解领土。

本参考的目标是：

> 在大规模执行前，尽量缩小地图与领土之间的差距。

---

## 3.2 四类未知量

### Known Knowns：已知的已知

已经明确知道并写入任务的信息。

例如：

- 使用 PostgreSQL；
- 不允许破坏现有 API；
- 必须支持移动端；
- 修改必须通过现有测试。

处理方式：

- 写入任务合同；
- 转化为明确约束；
- 纳入验收标准。

---

### Known Unknowns：已知的未知

已经意识到，但尚未决定或调查清楚的问题。

例如：

- 使用队列还是同步处理；
- 是否支持多租户；
- 数据保留多长时间；
- 是否允许修改数据库结构。

处理方式：

- 调查；
- 比较方案；
- 请求人类决策；
- 在实施前解决高影响问题。

---

### Unknown Knowns：未知的已知

人类实际上拥有判断能力，但尚未明确表达的信息。

常见表现：

- “我说不清想要什么，但看到就知道对不对。”
- “这个页面感觉不对。”
- “这个流程不符合实际工作习惯。”
- “以前项目一直是这样处理的，但没有写进文档。”

处理方式：

- 生成多个低成本原型；
- 提供对比方案；
- 使用截图、代码或现有产品作为参考；
- 通过反馈提取隐性偏好。

---

### Unknown Unknowns：未知的未知

人类和 Agent 一开始都没有意识到的问题。

例如：

- 历史数据中存在特殊格式；
- 某个模块有隐藏兼容逻辑；
- 第三方 API 有未记录限制；
- 某项修改会触发权限漏洞；
- 某个字段实际上被外部系统依赖。

处理方式：

- Blind Spot Pass；
- 搜索代码、测试、文档和历史修改；
- 检查依赖关系；
- 做最小实验；
- 在实施前主动寻找反例。

---

# 4. 适用场景

本参考适用于：

- 新功能开发；
- 跨模块重构；
- 不熟悉的代码库；
- 模糊需求；
- Agent 长时间自主执行任务；
- 涉及数据迁移的任务；
- 需要修改现有业务逻辑的任务；
- 用户无法准确描述最终效果的 UI 或产品任务；
- 需要从探索逐步收敛的任务；
- 失败后返工成本较高的任务。

尤其适用于：

> Agent 预计需要修改多个文件、理解历史逻辑或连续执行多个步骤的任务。

---

# 5. 不适用场景

以下任务不必完整运行本参考：

- 修改一个明确的拼写错误；
- 格式化代码；
- 修改一个已经定位的问题；
- 执行确定性命令；
- 更新一条静态文案；
- 用户已提供完整实现规格；
- 改动范围小、可逆且容易验证。

对于简单任务，可以跳过本文。对于中等复杂任务，优先使用本文末尾的 Quick Start 精简流程。

# 6. 总体执行流程

```text
任务输入
  ↓
建立初始任务地图
  ↓
Blind Spot Pass
  ↓
识别四类未知量
  ↓
Reverse Interview
  ↓
原型 / 参考物 / 调查
  ↓
解决高影响决策
  ↓
Implementation Plan
  ↓
计划审核门
  ↓
实施
  ↓
Deviation Log
  ↓
自动验证
  ↓
结果审核
  ↓
Post-implementation Quiz
  ↓
合并 / 发布 / 进入下一轮
```

# 7. 阶段一：建立初始任务地图

正式执行前，Agent 必须先整理当前已知信息。

## 输入

- 用户目标；
- 项目背景；
- 当前代码库；
- 相关文档；
- 已知约束；
- 参考实现；
- 验收目标。

## Agent 输出

```markdown
## Current Understanding

### Goal
任务最终需要实现什么。

### Current State
系统目前是什么状态。

### Known Constraints
已经明确的约束。

### Assumptions
当前暂时采用的假设。

### Missing Information
目前明确缺少的信息。

### Expected Deliverables
预计交付内容。
```

## 规则

- 不得把假设写成事实；
- 不得在未检查代码库时声称理解现有架构；
- 不得立即开始大规模修改；
- 必须区分用户明确要求和 Agent 自己推断。

---

# 8. 阶段二：Blind Spot Pass

## 目标

主动寻找可能改变实施方案的未知条件。

Blind Spot Pass 不是列出所有可能问题，而是寻找：

> 一旦答案不同，就会改变架构、范围、数据结构、风险或验收标准的问题。

## Agent 应检查

根据任务类型选择：

- 项目目录结构；
- 相关代码模块；
- 测试；
- 数据模型；
- 配置文件；
- API；
- 权限逻辑；
- 历史迁移；
- Git 历史；
- 相关任务记录；
- 已知问题；
- 外部依赖文档；
- 生产环境约束。

## 输出格式

```markdown
## Blind Spot Pass

| 盲点 | 为什么重要 | 可能影响 | 建议动作 | 风险等级 |
|---|---|---|---|---|
| 示例问题 | 原因 | 架构/数据/安全等 | 调查或决策 | 高/中/低 |
```

## 优先级判断

优先报告以下问题：

1. 会造成数据损坏的问题；
2. 会改变架构的问题；
3. 会影响安全或权限的问题；
4. 会改变核心用户流程的问题；
5. 会造成大量返工的问题；
6. 会影响项目成本或运行成本的问题；
7. 会改变验收定义的问题。

---

# 9. 阶段三：Reverse Interview

## 目标

由 Agent 主动向人类提问，解决会改变整体方向的问题。

## 提问规则

- 优先问高影响问题；
- 一次集中处理一个决策主题；
- 不询问 Agent 可以自行解决的低风险细节；
- 问题必须说明为什么重要；
- 尽可能提供选项及其影响；
- 不得无限提问；
- 不得用提问代替代码库调查。

## 好问题格式

```markdown
### Decision Required

**问题：**
系统是否需要支持多租户？

**为什么重要：**
这会影响数据库结构、权限模型和 API 设计。

**选项：**

A. 单租户
- 实现更简单
- 后续升级多租户成本高

B. 从第一版开始支持多租户
- 初始复杂度更高
- 架构更稳定

**Agent 建议：**
如果产品明确会服务多个组织，建议选择 B。
```

## 不应询问的问题

- 文件应该叫什么名字；
- 无关紧要的变量命名；
- Agent 可从现有代码风格判断的问题；
- 可以通过测试确定的问题；
- 不影响任务结果的格式偏好。

---

# 10. 阶段四：原型探测隐性偏好

## 适用情况

当用户出现以下表达时，应优先使用原型：

- “我不知道怎么描述。”
- “先做出来看看。”
- “感觉不对。”
- “想要更现代一些。”
- “我不确定流程应该怎样。”
- “有几个方向都可以。”

## 原型要求

原型必须：

- 成本低；
- 可快速生成；
- 差异明显；
- 不追求完整；
- 用于做选择，而不是直接作为最终实现。

## 可用原型形式

- 静态 HTML；
- 简化页面；
- 流程图；
- 数据结构草案；
- API 示例；
- CLI 交互示例；
- 伪代码；
- 文字版用户流程；
- 多种算法行为示例。

## 推荐输出

```markdown
## Prototype Directions

### Direction A
核心理念、优点、风险。

### Direction B
核心理念、优点、风险。

### Direction C
核心理念、优点、风险。

### Questions for Selection
- 哪个方向最接近目标？
- 哪些部分明显错误？
- 是否需要组合两个方向？
```

## 规则

原型之间必须有实质差异，不得只是改变颜色、命名或轻微布局。

---

# 11. 阶段五：使用高信息密度参考物

## 原则

参考物通常比抽象语言描述包含更多结构信息。

优先使用：

- 现有代码；
- 类似功能；
- 已有页面；
- 截图；
- 数据样本；
- 测试案例；
- API 返回示例；
- 用户真实操作录像；
- 历史项目；
- 外部开源实现。

## Agent 必须区分

### 需要复用的内容

- 架构模式；
- 交互逻辑；
- 数据结构；
- 错误处理；
- 视觉层级；
- 测试方式。

### 不应机械复制的内容

- 品牌；
- 文案；
- 不兼容的依赖；
- 历史技术债；
- 授权不明确的代码；
- 与当前产品目标冲突的设计。

## 输出

```markdown
## Reference Analysis

### Useful Patterns
可以借鉴的结构。

### Incompatible Elements
不能直接采用的部分。

### Adaptation Plan
如何适配当前项目。
```

# 12. 阶段六：Implementation Plan

在开始正式修改前，Agent 必须输出实施计划。

## 必须包含

```markdown
# Implementation Plan

## 1. Goal
最终目标。

## 2. Scope
本次包含和不包含的内容。

## 3. Current System Understanding
对现有系统的理解。

## 4. Resolved Unknowns
已经解决的未知量。

## 5. Remaining Assumptions
仍需暂时采用的假设。

## 6. Human Decisions
需要人类确认的决策。

## 7. Proposed Architecture
拟采用的架构或实现逻辑。

## 8. Files and Components
预计修改的文件和模块。

## 9. Implementation Steps
按顺序列出执行步骤。

## 10. Validation Plan
如何验证结果。

## 11. Rollback Plan
失败时如何恢复。

## 12. Risks
已知风险及缓解方案。
```

## 决策与执行分离

计划应将内容分成两类：

### 人类决策

包括：

- 架构；
- 数据模型；
- 权限；
- 外部接口；
- 用户体验方向；
- 不可逆变化；
- 成本明显变化；
- 范围变化。

### Agent 自主执行

包括：

- 文件组织；
- 局部函数拆分；
- 代码格式；
- 测试补充；
- 命名；
- 可逆的小型实现细节。

---

# 13. 计划审核门

Agent 不得在以下事项未解决时直接开始高风险实施：

- 目标不明确；
- 核心数据结构未确定；
- 存在不可逆迁移；
- 权限边界不明确；
- 关键依赖未知；
- 验收标准缺失；
- 任务范围存在明显冲突。

## 审核通过条件

计划必须满足：

- 目标明确；
- 关键未知量已处理；
- 未处理假设已明确记录；
- 风险可接受；
- 验证方式可执行；
- 回滚方式存在；
- 修改范围合理。

---

# 14. 阶段七：Deviation Log

实施过程中，Agent 必须记录与原计划不一致的情况。

推荐文件：

`implementation_notes.md`

## 记录格式

```markdown
# Implementation Notes

## Deviation 001

### Original Plan
原计划是什么。

### New Finding
执行中发现了什么。

### Decision
采取了什么处理。

### Reason
为什么这样处理。

### Impact
对范围、架构、测试或风险的影响。

### Risk Level
Low / Medium / High

### Requires Human Review
Yes / No
```

# 15. 偏差风险分级

## Level 1：低风险偏差

特点：

- 可逆；
- 局部；
- 不改变任务目标；
- 不影响数据；
- 不改变公开接口；
- 容易验证。

示例：

- 调整内部函数结构；
- 修改局部命名；
- 增加辅助测试；
- 替换等价实现。

处理方式：

> 记录后继续执行。

---

## Level 2：中风险偏差

特点：

- 修改多个模块；
- 影响内部接口；
- 需要额外依赖；
- 增加维护成本；
- 验证复杂度提高；
- 与原计划存在实质差异。

处理方式：

> 记录，选择最小可逆方案继续；在最终报告中重点说明。

如果存在多个明显不同的方案，应请求人类决策。

---

## Level 3：高风险偏差

特点：

- 数据迁移；
- 删除数据；
- 权限或安全变化；
- 改变公开 API；
- 改变核心架构；
- 明显增加费用；
- 扩大任务范围；
- 破坏向后兼容；
- 无法回滚；
- 与用户目标冲突。

处理方式：

> 停止相关实施，报告发现、影响和可选方案，等待人类决策。

不得以“保持自主执行”为理由跨越高风险边界。

---

# 16. 阶段八：实施规则

实施时，Agent 应遵守：

1. 优先最小改动；
2. 不随意扩大范围；
3. 保留现有行为，除非任务明确要求改变；
4. 每完成一个可验证阶段就运行测试；
5. 不把警告当作成功；
6. 不绕过失败测试；
7. 不删除未知代码来让测试通过；
8. 不隐藏未解决问题；
9. 所有偏差写入记录；
10. 保持实现与任务合同一致。

---

# 17. 阶段九：自动验证

验证必须对应任务风险，而不是只运行一个通用测试命令。

## 验证层级

### 静态验证

- 格式检查；
- 类型检查；
- lint；
- schema 检查；
- 配置检查。

### 单元验证

- 核心函数；
- 边界条件；
- 错误处理；
- 新增逻辑。

### 集成验证

- 模块之间交互；
- 数据库；
- API；
- 队列；
- 外部服务。

### 行为验证

- 用户流程；
- UI；
- CLI；
- 实际输入输出；
- 回归场景。

### 风险验证

- 权限；
- 安全；
- 数据一致性；
- 并发；
- 性能；
- 回滚。

## 验证输出

```markdown
## Validation Report

| 验证项 | 结果 | 证据 | 备注 |
|---|---|---|---|
| 类型检查 | Pass | 命令输出 | |
| 单元测试 | Pass | 42 tests | |
| 边界场景 | Pass | 示例 | |
| 手动流程 | Partial | 缺少生产凭据 | 需后续验证 |
```

不得把未运行的验证写成通过。

Agent 完成任务后必须输出：

```markdown
## Why
核心设计理由。

## Differences From Plan
与原计划的不同。

修改文件。

## Assumptions

如何回滚。

```

# 19. Post-implementation Quiz

## 目的

确认人类真正理解 Agent 做了什么，而不是只看到“测试通过”。

Quiz 应重点考察：

- 核心架构；
- 数据流；
- 关键决策；
- 已知限制；
- 偏差；
- 风险；
- 回滚方式。

## 示例

```markdown
## Understanding Quiz

1. 本次修改解决的核心问题是什么？
2. 新的数据是如何在系统中流动的？
3. 为什么选择方案 A，而不是方案 B？
4. 哪个假设如果不成立，会导致当前实现失效？
5. 本次修改中风险最高的部分是什么？
6. 如果上线后出现问题，应如何回滚？
7. 哪些场景目前还没有被完整验证？
```

## 使用方式

Quiz 不是形式上的考试。

如果人类无法回答，应要求 Agent：

- 重新解释；
- 用流程图说明；
- 提供具体例子；
- 指向相关代码；
- 简化技术术语。

# 22. 可复制提示词

## 22.1 启动 Unknowns-First 流程

```text
请对当前任务使用 Unknowns-First Agentic Workflow。

不要立即开始实施。先建立当前任务地图，然后执行 Blind Spot Pass，识别可能改变实施方案的关键未知量。

请将未知量分为：
1. 已知的已知；
2. 已知的未知；
3. 未知的已知；
4. 未知的未知。

优先报告会影响架构、数据、安全、兼容性、成本、范围和验收标准的问题。
```

---

## 22.2 Blind Spot Pass

```text
在开始实施前，请检查相关代码、测试、文档、数据结构和依赖，执行一次 Blind Spot Pass。

不要列出所有想得到的问题。只列出那些答案不同就可能改变实施路线、架构、数据结构、风险或验收标准的问题。

对于每个盲点，说明：
- 为什么重要；
- 可能造成什么影响；
- 建议如何解决；
- 风险等级。
```

---

## 22.3 Reverse Interview

```text
请根据当前任务采访我。

优先询问会改变整体方案方向的问题，例如架构、数据、权限、兼容性、成本、失败处理和验收标准。

不要询问你可以通过检查代码库自行解决的问题，也不要询问低影响的实现细节。

每个问题请说明：
- 为什么需要这个答案；
- 可选方案；
- 每个方案的影响；
- 你的推荐。
```

---

## 22.4 原型探测

```text
我目前无法准确描述最终效果。

请先生成 3 至 4 个差异明显的低成本原型或方案，用于帮助我识别自己的隐性偏好。

这些原型不需要完整，但必须在核心逻辑、用户流程、架构或设计方向上有明显区别。

请说明每个原型：
- 核心方向；
- 优点；
- 缺点；
- 最适合什么场景。
```

---

## 22.5 实施计划

```text
在修改代码前，请先输出 Implementation Plan。

计划必须包括：
- 当前理解；
- 任务范围；
- 已解决的未知量；
- 剩余假设；
- 需要我决定的事项；
- 拟采用的架构；
- 修改文件；
- 实施步骤；
- 验证方案；
- 回滚方案；
- 已知风险。

请把必须由我拍板的高影响决策放在最前面。低风险、可逆的执行细节由你自行决定。
```

---

## 22.6 偏差记录

```text
实施过程中请维护 implementation_notes.md。

当实际情况与计划不一致时，记录：
- 原计划；
- 新发现；
- 实际决定；
- 决定原因；
- 影响；
- 风险等级；
- 是否需要人工审核。

低风险、可逆的偏差可以记录后继续。

涉及数据、权限、安全、公开接口、架构、兼容性、明显成本变化或不可逆操作的偏差，必须停止相关实施并请求决策。
```

---

## 22.7 实施后审核

```text
完成后请输出 Implementation Report 和 Validation Report。

必须明确区分：
- 已验证；
- 部分验证；
- 未验证；
- 无法验证。

不要将未运行的测试描述为通过。
```

---

## 22.8 理解测验

```text
请根据本次实际改动，对我进行一次理解测验。

问题应覆盖：
- 核心设计；
- 数据流；
- 关键决策；
- 与原计划的偏差；
- 已知风险；
- 回滚方式；
- 尚未验证的部分。

如果我回答错误，请指出误解并重新解释相关部分。
```

# 23. 验收标准

本参考流程被正确执行时，应满足：

- Agent 没有一开始就直接修改；
- 初始假设被明确列出；
- 高影响未知量被主动识别；
- 人类只处理真正需要决策的问题；
- 隐性偏好通过原型或参考物被暴露；
- 实施前存在可审核计划；
- 执行偏差被记录；
- 高风险偏差没有被擅自处理；
- 测试与风险对应；
- 未验证内容被明确标注；
- 最终结果与任务合同一致；
- 人类能够解释主要改动和风险。

# 24. 常见失败模式

## 失败模式 1：把 Blind Spot Pass 变成泛泛而谈

表现：

- 列出几十个通用风险；
- 与当前代码无关；
- 没有检查实际项目。

修正：

> 所有盲点必须绑定具体代码、数据、依赖或业务条件。

---

## 失败模式 2：无限采访用户

表现：

- 每个细节都请求确认；
- Agent 不愿自行判断；
- 项目无法推进。

修正：

> 只询问会改变整体方向的问题。可逆的局部决定由 Agent 自行处理。

---

## 失败模式 3：计划写得很长但无法审核

表现：

- 大量空泛描述；
- 没有关键决策；
- 没有文件范围；
- 没有验证方案。

修正：

> 计划必须能回答“改哪里、为什么、怎么验证、失败如何恢复”。

---

## 失败模式 4：偏差日志沦为流水账

表现：

- 记录所有小操作；
- 重要偏差反而不突出。

修正：

> 只记录影响计划、架构、风险、范围或验证的偏差。

---

## 失败模式 5：为了不中断而跨越风险边界

表现：

- Agent 擅自迁移数据；
- 修改权限；
- 删除兼容逻辑；
- 改变公开 API。

修正：

> 自主执行不等于拥有无限决策权。高风险偏差必须暂停。

---

## 失败模式 6：测试通过等于任务成功

表现：

- 测试覆盖不完整；
- 用户流程未验证；
- 验收标准没有检查。

修正：

> 同时验证技术正确性、用户行为和任务合同。

---

## 失败模式 7：Quiz 变成技术冷知识考试

表现：

- 考函数名；
- 考无关实现细节；
- 对理解系统没有帮助。

修正：

> Quiz 应验证人类是否理解设计、风险、数据流和回滚方式。

# 25. Quick Start 精简版

对于中等复杂任务，可以只执行以下五步。

## Step 1：当前理解

```text
先总结你对任务、现有系统、约束和验收标准的理解。明确列出假设。
```

## Step 2：盲点扫描

```text
检查项目后，找出最多五个可能改变实施方案的关键未知量。
```

## Step 3：计划

```text
输出实施步骤、修改范围、风险、验证方式和回滚方式。
```

## Step 4：执行与偏差记录

```text
低风险偏差记录后继续；高风险偏差暂停并报告。
```

## Step 5：验证与解释

```text
运行验证，报告实际改动、剩余风险，并通过几个问题确认我理解了结果。
```

# 27. 与 Codex Engineering Starter Kit 的配合方式

本参考不是第四个 Skill。它只作为 `start-task` 的可选参考材料。

默认使用方式：

```text
start-task
  ↓
如有明显未知量，先使用 Quick Start 五步版
  ↓
生成或完善任务合同
  ↓
提交轻量实施计划
  ↓
用户批准
  ↓
Codex 在批准范围内执行
  ↓
记录重要偏差
  ↓
review-task
```

只有当 Quick Start 不足以处理风险时，Codex 才应询问用户是否启用完整版。

本参考负责的是：

> 在 Codex 开始较大改动前，确保人和 Codex 对任务拥有足够准确的共同地图。

# 28. 最终原则

1. 不要把模糊需求直接交给强 Agent。
2. 不要假设人类已经知道所有重要问题。
3. 不要用更长的提示词掩盖认知缺口。
4. 优先处理会改变方案的未知量。
5. 用原型发现无法语言化的偏好。
6. 用参考物提高信息密度。
7. 把人类决策与 Agent 执行分开。
8. 低风险偏差可以自主处理。
9. 高风险偏差必须保留给人类。
10. 任务结束不仅要验证系统，也要验证人的理解。

核心总结：

> 更强的 Agent 不会消除未知量，只会更快地放大未知量。
> Agentic Engineering 的关键不是让 Agent 做更多，而是让系统更早发现错误方向。
